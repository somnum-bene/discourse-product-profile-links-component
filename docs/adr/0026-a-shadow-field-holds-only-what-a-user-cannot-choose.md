# A Shadow Field holds only what a User cannot choose

> **Settles the three questions #59 and #61 deferred into #62, before the build assumes an answer to any of them.** It does not revisit the configuration: [ADR-0024](0024-a-shadow-text-field-must-be-visible-to-be-readable.md) measured both flags against the instance and fixed them, and [ADR-0025](0025-a-freeze-stops-the-wipe-so-it-covers-the-migration-not-the-feature.md) established that the Shadow Field is the standing answer and the freeze is not.

Three questions were left open because they only become answerable once the build decision is made. Each has an expansive reading and a narrow one, and the second of them roughly doubles the work. One sentence settles all three: **a Shadow Field is the home for a value a User cannot choose, and for nothing else.** Every answer below is that rule applied.

## The Shadow Field replaces the dropdown as a Collection Link's destination

#28 translates roughly 124,500 members' legacy equipment selections into the three columns Discourse asked for — member identifier, custom field name, value — and Discourse's team applies them. That pass currently writes every value into `Machine` and `Mask`, which are `dropdown`-typed.

For a row at `disposition: collection`, it now names the Shadow Field in the second column instead. Every other disposition still writes the Managed Field, so the pass keeps its shape entirely: one file, three columns, the same idempotence, the same regenerate-against-a-fresh-export rule. What changes is a routing rule, not a mechanism.

The alternative — write into the dropdown as planned, then mirror into the Shadow Field afterwards — was rejected on three counts. A Collection Link is off-list *the instant it lands* ([ADR-0021](0021-a-collection-link-is-a-mapping-with-no-option.md)), so "follow" writes the value into the one field that cannot keep it and leaves it there, unprotected, for the whole interval between the two passes. The mirror pass needs a second join against a member export, and #28 records that member identifiers are regenerated by every import run — a second export is a second perishable artifact to keep in step with the first. And it leaves a doomed copy behind permanently: the dropdown holds the value until a profile save clears it, so the fallback's "the Managed Field is empty" branch becomes the ordinary production path rather than the rare one, and the two sources disagree routinely rather than transiently.

Writing it once, into the field that can hold it, costs one word in a repository that is already doing the join.

**What this does not reach.** A holder whose dropdown value has *already* been wiped between now and the migration has nothing in a Discourse export to translate — their legacy selection survives only in the CPAPTalk dump, which Discourse's team holds. Recovering them means the import pass reads the dump rather than a Discourse export. That is stated here because it is a real gap and the decision does not close it; it is outside this repository either way.

## It holds Collection Link values and not a mirror of the dropdown

The expansive reading — every curated value gets a durable copy, making the Shadow Field a general-purpose mirror — is rejected.

It protects nothing extra. The wipe is `clean_custom_field_values` resolving an off-list value through `find_by_value` to `nil`; a value that is *on* the option list resolves to itself and is not at risk. The population the mirror would add is exactly the population that was never in danger.

It would also be wrong rather than merely redundant. A Managed Field is `editable: true` and a Shadow Field is `editable: false`, and nothing between import runs keeps the two in step — this repository never writes a User's values at all. So a User who buys a new machine updates the dropdown and *cannot* update the mirror, and the mirror is stale from that moment. If they later clear the dropdown, the fallback fires and renders the machine they used to own, confidently, with a working link. Absent is a Profile Link missing; stale is a Profile Link lying, and the second is worse than the defect being fixed.

Confining the Shadow Field to values that have no Dropdown Option behind them removes that case by construction rather than by discipline: there is no live value for it to contradict, because a User cannot select one. It also settles the disagreement rule the build needs — **the Managed Field wins whenever it holds anything at all** — and makes that a tie-break for a transient state rather than a policy with consequences.

That rule is deliberately narrower than "whenever it resolves". A Managed Field holding an **Unmatched Value** wins too, and does not fall through: an Unmatched Value is equipment the User has *now*, while the Shadow Field holds what the migration wrote and what no User can edit. Falling through would swap what somebody owns for what they used to own, and link it — the stale-is-lying failure again, arriving by a different door. The fallback fires on an empty Managed Field and on nothing else, which is precisely the state the #58 wipe leaves behind.

Narrow is also the reversible direction. Widening later needs no data migration, because the values it would add were already safe; narrowing later would mean deciding which stored values to abandon.

## One Shadow Field per Managed Field

A User can hold a discontinued machine and a discontinued mask at the same time, and one Custom User Field holds one string. A single shared Shadow Field therefore cannot represent them, and would silently keep whichever value the migration wrote second. That settles it by itself.

The second reason is structural. A Field Mapping associates one Custom User Field with the Mappings that resolve its values ([ADR-0002](0002-config-adapter-joins-settings-with-site-user-fields.md)); a shared field would need the union of both fields' Mappings, which makes a mask value resolvable in a machine's slot and removes the scoping that keeps the two apart today.

The cost of the decision is one extra Custom User Field on the instance. There is no per-field code: which Shadow Field feeds which Link Surface row is configuration, in the same setting that already names the Managed Field.

The names are `Machine (Discontinued)` and `Mask (Discontinued)`. They are near-invisible in practice — a Link Surface hides core's plain-text row whenever it renders a link for that Field Mapping — so this is an administrator-facing choice, and the suffix names the population the field exists for.

## Two consequences the build must carry

Neither is in #62's scope list and both fall straight out of the rule above.

**The Profile Link is labelled with the Managed Field's name.** `ProfileLinkRow` renders `{{@link.fieldName}}:`, so a fallback carrying the Shadow Field's name would read `Machine (Discontinued): AirSense 10 Elite with HumidAir (Discontinued)`. A fallback changes where a value came from, not which link it is, and the label follows the link.

**The Shadow Field's own core row is hidden when, and only when, the fallback renders.** The field is `show_on_profile: true` by force, so Discourse core renders it as plain text alongside our link, and leaving it there shows the same value twice. Hiding it unconditionally is worse: `core-field-rows.ts` already argues that hiding a row with no Profile Link behind it takes a value off the profile entirely, and "showing a value twice is a blemish; silently deleting one is data loss." So the row is hidden on exactly the condition that a link replaced it — the rule the Managed Field's own row already follows.

## What follows for the rest of the pipeline

**A Shadow Field is not a Managed Field**, and `CONTEXT.md` now carries the term. The Sheet Export allowlist names `Machine` and `Mask`; a Catalogue Apply never writes a Shadow Field and `dropdownOptionsFor` cannot reach one, for the same structural reason it cannot emit a Collection Link (ADR-0021).

**The Disposition Table gains a column, not rows.** It stays one row per legacy option value — a table of only the Collection Links would be missing most of what the join needs while looking complete ([ADR-0023](0023-the-disposition-table-is-stricter-than-the-runtime.md)) — and gains the Custom User Field name the value must be *written* to, which is the Shadow Field on a `collection` row and the Managed Field on every other. The alternative was to let the private repository derive the destination from the disposition plus a naming convention, which puts a rule this repository owns into a consumer that cannot see it change. The Disposition Table is the entire interface; an interface states its own fields.

**The `RETAINED` line moves its terminus again.** #61 corrected it to name the profile save as the point a retained value dies, and the editability flag as the thing that stops it. A Shadow Field stops it too, permanently and without taking self-service editing away, so the line names that rather than leaving a freeze as the only answer on offer.

## What is not settled here

**The migration-window freeze stays an operator step.** ADR-0025 left automating it undesigned, and nothing here designs it.

**Whether a Shadow Field is created by hand, by `apply:catalogue`, or by a migration.** A Catalogue Apply pushing Dropdown Options is a different kind of write from one creating a Custom User Field, and creating a field on a live instance is a destructive-write question under [ADR-0013](0013-a-destructive-write-is-authorised-by-what-it-removes.md) that nothing has been argued for. The build reports a Shadow Field that is missing or misconfigured and does not repair it.
