# A Shadow Field holds only what a User cannot choose

> **Settles the three questions #59 and #61 deferred into #62, before the build assumes an answer to any of them.** It does not revisit the configuration: [ADR-0024](0024-a-shadow-text-field-must-be-visible-to-be-readable.md) measured both flags against the instance and fixed them, and [ADR-0025](0025-a-freeze-stops-the-wipe-so-it-covers-the-migration-not-the-feature.md) established that the Shadow Field is the standing answer and the freeze is not.

Three questions were left open because they only become answerable once the build decision is made. Each has an expansive reading and a narrow one, and the second of them roughly doubles the work. One sentence settles all three: **a Shadow Field is the home for a value a User cannot choose, and for nothing else.** Every answer below is that rule applied.

## The Shadow Field replaces the dropdown as a Collection Link's destination

#28 translates roughly 124,500 members' legacy equipment selections into the three columns Discourse asked for — member identifier, custom field name, value — and Discourse's team applies them. That pass currently writes every value into `Machine` and `Mask`, which are `dropdown`-typed.

For a row at `disposition: collection`, it now names the Shadow Field in the second column instead. Every other disposition still writes the Managed Field, so the pass keeps its shape entirely: one file, three columns, the same idempotence, the same regenerate-against-a-fresh-export rule. What changes is a routing rule, not a mechanism.

The alternative — write into the dropdown as planned, then mirror into the Shadow Field afterwards — was rejected on three counts. A Collection Link is off-list _the instant it lands_ ([ADR-0021](0021-a-collection-link-is-a-mapping-with-no-option.md)), so "follow" writes the value into the one field that cannot keep it and leaves it there, unprotected, for the whole interval between the two passes. The mirror pass needs a second join against a member export, and #28 records that member identifiers are regenerated by every import run — a second export is a second perishable artifact to keep in step with the first. And it leaves a doomed copy behind permanently: the dropdown holds the value until a profile save clears it, so the fallback's "the Managed Field is empty" branch becomes the ordinary production path rather than the rare one, and the two sources disagree routinely rather than transiently.

Writing it once, into the field that can hold it, costs one word in a repository that is already doing the join.

**What this does not reach.** A holder whose dropdown value has _already_ been wiped between now and the migration has nothing in a Discourse export to translate — their legacy selection survives only in the CPAPTalk dump, which Discourse's team holds. Recovering them means the import pass reads the dump rather than a Discourse export. That is stated here because it is a real gap and the decision does not close it; it is outside this repository either way.

## It holds Collection Link values and not a mirror of the dropdown

The expansive reading — every curated value gets a durable copy, making the Shadow Field a general-purpose mirror — is rejected.

It protects nothing extra. The wipe is `clean_custom_field_values` resolving an off-list value through `find_by_value` to `nil`; a value that is _on_ the option list resolves to itself and is not at risk. The population the mirror would add is exactly the population that was never in danger.

It would also be wrong rather than merely redundant. A Managed Field is `editable: true` and a Shadow Field is `editable: false`, and nothing between import runs keeps the two in step — this repository never writes a User's values at all. So a User who buys a new machine updates the dropdown and _cannot_ update the mirror, and the mirror is stale from that moment. If they later clear the dropdown, the fallback fires and renders the machine they used to own, confidently, with a working link. Absent is a Profile Link missing; stale is a Profile Link lying, and the second is worse than the defect being fixed.

Confining the Shadow Field to values that have no Dropdown Option behind them removes that case by construction rather than by discipline: there is no live value for it to contradict, because a User cannot select one. It also settles the disagreement rule the build needs — **the Managed Field wins whenever it holds anything at all** — and makes that a tie-break for a transient state rather than a policy with consequences.

That rule is deliberately narrower than "whenever it resolves". A Managed Field holding an **Unmatched Value** wins too, and does not fall through: an Unmatched Value is equipment the User has _now_, while the Shadow Field holds what the migration wrote and what no User can edit. Falling through would swap what somebody owns for what they used to own, and link it — the stale-is-lying failure again, arriving by a different door. The fallback fires on an empty Managed Field and on nothing else, which is precisely the state the #58 wipe leaves behind.

Narrow is also the reversible direction. Widening later needs no data migration, because the values it would add were already safe; narrowing later would mean deciding which stored values to abandon.

## One Shadow Field per Managed Field

A User can hold a discontinued machine and a discontinued mask at the same time, and one Custom User Field holds one string. A single shared Shadow Field therefore cannot represent them, and would silently keep whichever value the migration wrote second. That settles it by itself.

The second reason is structural. A Field Mapping associates one Custom User Field with the Mappings that resolve its values ([ADR-0002](0002-config-adapter-joins-settings-with-site-user-fields.md)); a shared field would need the union of both fields' Mappings, which makes a mask value resolvable in a machine's slot and removes the scoping that keeps the two apart today.

The cost of the decision is one extra Custom User Field on the instance. There is no per-field code: which Shadow Field feeds which Link Surface row is configuration, in the same setting that already names the Managed Field.

The names are `Machine (Discontinued)` and `Mask (Discontinued)`. They are near-invisible in practice — a Link Surface hides core's plain-text row whenever it renders a link for that Field Mapping — so this is an administrator-facing choice, and the suffix names the population the field exists for.

## Two consequences the build must carry

Neither is in #62's scope list and both fall straight out of the rule above.

**The Profile Link is labelled with the Managed Field's name.** `ProfileLinkRow` renders `{{@link.fieldName}}:`, so a fallback carrying the Shadow Field's name would read `Machine (Discontinued): AirSense 10 Elite with HumidAir (Discontinued)`. A fallback changes where a value came from, not which link it is, and the label follows the link.

**The Shadow Field's own core row is hidden when, and only when, the fallback renders.** The field is `show_on_profile: true` by force, so Discourse core renders it as plain text alongside our link, and leaving it there shows the same value twice. Hiding it unconditionally is worse: `core-field-rows.ts` already argues that hiding a row with no Profile Link behind it takes a value off the profile entirely, and "showing a value twice is a blemish; silently deleting one is data loss." So the row is hidden on exactly the condition that a link replaced it — the rule the Managed Field's own row already follows.

## The third Link Surface needed nothing

ADR-0004 keeps three Link Surfaces and #62 names two. The post surface is the third, and it gets the fallback with no line of its own, because it already resolves through the same `profileLinksFor` the other two call and labels a row with `fieldName`. Its User Field Source fetches the author's fields from the same endpoint an anonymous reader was measured against, so the value reaches it on the same terms.

It hides no core row, and must not start. A post carries no core Custom User Field rows, so there is no duplicate there to remove — the "make the three consistent" change would have it search a whole topic for rows that do not exist. That is pinned by a test rather than left to be rediscovered.

## What follows for the rest of the pipeline

**A Shadow Field is not a Managed Field**, and `CONTEXT.md` now carries the term. The Sheet Export allowlist names `Machine` and `Mask`; a Catalogue Apply never writes a Shadow Field and `dropdownOptionsFor` cannot reach one, for the same structural reason it cannot emit a Collection Link (ADR-0021).

**The Disposition Table gains a column, not rows.** It stays one row per legacy option value — a table of only the Collection Links would be missing most of what the join needs while looking complete ([ADR-0023](0023-the-disposition-table-is-stricter-than-the-runtime.md)) — and gains `destination_field_name`, the Custom User Field the value must be _written into_ — the Shadow Field on a `collection` row and the Managed Field on every other. It is not called a target field: `CONTEXT.md` reserves that phrase away from **Managed Field**, and `target` already means a Dropdown Option set in the apply path. The alternative was to let the private repository derive the destination from the disposition plus a naming convention, which puts a rule this repository owns into a consumer that cannot see it change. The Disposition Table is the entire interface; an interface states its own fields.

**The `RETAINED` line moves its terminus again.** #61 corrected it to name the profile save as the point a retained value dies, and the editability flag as the thing that stops it. A Shadow Field stops it too, permanently and without taking self-service editing away, so the line names that rather than leaving a freeze as the only answer on offer.

## By hand, reported by the apply and never created by it

A Shadow Field is created by an Administrator at `/admin/config/user_fields`, once per instance. `apply:catalogue` reports one that is missing or misconfigured and repairs nothing; no Settings Migration creates one either.

That is a decision rather than a deferral, and it follows from what the two tools are for. A Catalogue Apply pushes Dropdown Options to fields that already exist, and [ADR-0013](0013-a-destructive-write-is-authorised-by-what-it-removes.md) authorises its writes by what they _remove_ — a rule with nothing to say about creating a field, which removes nothing and which no `--replace` flag could sensibly gate. A Settings Migration reaches the component's own settings and not the site's Custom User Fields at all. Adding field creation to either would put a new kind of write behind an authorisation story built for a different one, and it would run on every instance the command is ever pointed at.

It is also a one-line job done twice in the life of the project, against a checklist the apply prints for free. The cost of automating it is a new destructive-write argument; the cost of not automating it is two Administrators reading a `RETENTION` line.

## The freeze comes off last

ADR-0025 adopts a freeze for the duration of a Catalogue Apply that writes `Machine` and `Mask` wholesale. It stays an operator step and nothing here automates it, but the order it sits in is now fixed, because the Shadow Field changes what the window is protecting:

1. **Create both Shadow Fields**, in the forced configuration. Before anything else — a Collection Link written while they do not exist has nowhere to go but the `dropdown` that cannot keep it.
2. **Freeze `Machine` and `Mask`** — `editable: false`. Visibility is untouched, so the Link Surfaces keep rendering throughout.
3. **Catalogue Apply.** Dropdown Options are pushed; the four legacy catch-alls go, retained as Mappings.
4. **The translation pass writes values** (#28) — `collection` rows to the Shadow Fields, everything else to the Managed Fields. Staff writes go straight through the freeze, which ADR-0024 and ADR-0025 both confirmed.
5. **Thaw.**

The window that matters is 3 → 4, and it is why the freeze cannot come off early. Between the option removal and the value write, a Managed Field holds an off-list value with no Dropdown Option behind it and no copy anywhere; one User saving their profile in that gap loses it with nothing to restore from. After step 4 the Collection Link holders are safe permanently, and the freeze is the ordinary migration-hygiene measure ADR-0025 describes rather than the only thing standing between a value and `""`.

## Measured, anonymously

Run against `tyler-test.discourse.group` on 2026-09-14, with both Shadow Fields created in the forced configuration — `text`, `editable: false`, `show_on_profile: true`, `show_on_user_card: true`, `requirement: optional` — and confirmed by a fresh `GET` rather than any write's `200` ([ADR-0014](0014-a-write-is-confirmed-by-reading-it-back.md)). A throwaway non-staff User held `AirSense 10 Elite with HumidAir (Discontinued)` in `Machine (Discontinued)` with `Machine` itself empty, and was deleted afterwards.

An `Api-Key` carrying that User's `Api-Username` is genuinely that account, on #61's test: `/admin/config/user_fields.json` answered `404` on those credentials and `200` for the Administrator a moment later.

- **The value survives the save.** The non-staff User saved their own profile submitting `{ "2": "", "11": "" }` and the Shadow Field came back unchanged. The same request wrote `probe-humidifier` to an unrelated `editable: true` field, and _that_ landed — which is what proves the save was a real one rather than a request failing wholesale earlier. A later save submitting an actual value for the Shadow Field was refused the same way.
- **An anonymous reader gets it.** Read with no `Api-Key` and no cookie, `/u/<username>.json` carried the Shadow Field's value, and `/site.json` declared both Shadow Fields at `editable: false` with both visibility flags true.
- **It resolves to the Collection Link.** The anonymous payload, the anonymous `/site.json` field list and the shipped `settings.yml` default were fed through `readLinkConfig` and `resolveProfileLinks` unchanged: no Config Problems, both Shadow Fields joined, and one Profile Link — `Machine: AirSense 10 Elite with HumidAir (Discontinued)` to `https://www.cpap.com/collections/cpap-machines`, read from `Machine (Discontinued)`, with `Machine (Discontinued)` named as the core row to hide.

The throwaway User was deleted afterwards and the instance re-read: the Managed Fields unchanged at 8 and 47 options and still `editable: true`, no field at `for_all_users`, no User matching the probe's name. The `probe-humidifier` value written during the save control was a value _on that User_, so it went with them; the `Humidifier` field itself was never altered.

**What this did not reach.** The instance runs the previously released component, so no signed-out browser has rendered a fallback on a user profile or a user card. What is verified against the instance is the half ADR-0024 calls the one that bites — that an anonymous reader receives the value — and that the shipped configuration turns that exact payload into the right Profile Link. The step from a resolved Profile Link to markup is the same one the two surfaces already take for every other value, is unchanged by this work, and is covered by unit tests. Deploying this component to the instance and viewing a profile signed out would close the remaining gap, and it has not been done.

### The trap that makes an anonymous check lie

`hide_new_user_profiles` is on, and it hides a new, trust-level-0 User's profile from anonymous readers **entirely** — `user_fields` is absent from the payload, not empty. A throwaway User created for this check is exactly that User.

The first anonymous read here came back with no `user_fields` at all, which is byte-for-byte the symptom ADR-0024 describes for a Shadow Field hidden from profile and card. It was not that: a populated `Machine`, a Managed Field visible on both surfaces since long before any of this, was missing from the same payload. Raising the throwaway User's trust level made every field appear at once.

Anyone re-running this must raise the trust level first, and must read a _populated Managed Field_ in the same payload as a control. Without that control the check reports the forced configuration as broken, and the obvious conclusion — that ADR-0024's visibility finding is wrong — is the wrong one.

## What is not settled here

**The migration-window freeze stays an operator step.** ADR-0025 left automating it undesigned, and nothing here designs it.

**Nothing about the Collection Assignment.** A Shadow Field holds a value the curated table already decided; it adds no row to it and asks a curator nothing new.
