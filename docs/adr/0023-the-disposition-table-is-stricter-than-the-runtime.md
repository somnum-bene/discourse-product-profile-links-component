# The disposition table is stricter than the runtime, deliberately

> **Refines [ADR-0013](0013-a-destructive-write-is-authorised-by-what-it-removes.md)** rather than superseding it, and applies its reasoning to a boundary it never had to consider: a consumer outside this repository. Required by the **Disposition Table** (#40), which is the interface described in #28.

Profile Link resolution is an exact **trimmed** match on both sides. `javascripts/discourse/lib/profile-links.ts` trims each Mapping value on the way into `urlsByValue` and trims the stored value again before the lookup, so a Mapping value carrying a leading space resolves for a member holding the same name without one. `linkCovering` in `scripts/lib/plan-apply.ts` trims for exactly that reason: a plan that judged coverage with a bare `===` would report a Profile Link as missing that a member is in fact receiving.

The gate on the **Disposition Table** does the opposite. `spec/unit/disposition-table.test.ts` compares each row's value against the shipped `settings.yml` with `toBe` on raw strings — no trimming, no normalising anywhere in the comparison — and `readDispositionTable` refuses a row whose value and URL do not pair. Held against the paragraph above, that looks like two parts of one pipeline disagreeing about what "the same value" means, and the obvious tidy-up is to relax the gate until it agrees with `linkCovering`.

That tidy-up would remove the only guarantee the downstream join has, and this ADR exists to say so before someone performs it.

The asymmetry is not an inconsistency, because the two comparisons answer questions asked by different consumers. `linkCovering` asks *will this member's stored value resolve on this instance*, and the honest answer is the runtime's own rule, whatever the runtime tolerates. The disposition table's gate asks *can a repository we cannot see reproduce this string*, and the runtime's tolerance is not available to that repository: it holds a member export, it performs its own join, and it writes a value into a Custom User Field. Nothing on that side trims anything on our behalf. A value that differs from the shipped Mapping by one byte is written successfully, stores without complaint, and renders no link — which is precisely the failure #28 exists to remove, arriving through the mechanism built to prevent it.

So being stricter than what would work is the point. The gate is not asserting that a looser match would fail; it is asserting that we never have to find out.

This is ADR-0013's own move in the other direction. That decision keeps a deliberately *looser* comparison — two options compared with every non-alphanumeric character dropped — purely so an operator can tell four unrelated products from four differently-typed spellings, and fences it off from the matching path entirely: "the moment it influenced a write, 'close enough' would be shipping to a dropdown." Here a deliberately *stricter* comparison is fenced off from the resolution path for the mirror reason. Neither is the runtime's rule, and neither is allowed anywhere near it. ADR-0013's "exact matching is not negotiable" is a statement about what reaches a Mapping, not an instruction to make every comparison in the repository identical.

## What follows from it

The suffix is already safe and the base name is not. `readCollectionLinks` refuses any value in `data/collection-links.csv` that does not end in exactly the bytes of `COLLECTION_LINK_SUFFIX`, so ` (discontinued)` or a missing leading space cannot reach `settings.yml` at all. Nothing upstream checks the base name against the shipped Mapping, because until this table existed no consumer needed the two compared. The gate on the disposition table is where that comparison lives, and it is the reason the file is committed rather than generated by whoever consumes it: a reviewed artifact can be gated, and a generated one is gated by whatever generated it.

An unlinked row is held to the opposite rule, and it is the same decision. Its value must equal the legacy display text byte for byte, and must **not** appear among the shipped Mapping values. The second half is what catches ` (Discontinued)` being appended to a value that is not a link — a string that looks like a **Collection Link**, is not one, and either resolves to a collection nobody curated for that member or resolves to nothing. ADR-0020 puts the suffix on a Collection Link's value because the value is its own anchor text; a value with no anchor text has no claim on it.

## What this does not change

Nothing about resolution. The runtime's trimmed match stays as it is, `linkCovering` keeps trimming, and no gate here is a reason to tighten either — a stricter runtime would start refusing Mappings that work today, which is the change this ADR is written to prevent, applied to the wrong side.
