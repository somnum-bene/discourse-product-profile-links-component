# A Collection Link is a Mapping with no Dropdown Option

> **Refines [ADR-0011](0011-dropdown-options-are-a-second-sink-applied-per-site.md)** rather than superseding it. The invariant it protects survives; the equality it was implemented as does not. Required by [ADR-0020](0020-discontinued-equipment-links-to-a-collection.md).

A **Collection Link** must resolve for a member who already holds the value and must never be offered to a member choosing one. That is a **Mapping** with no **Dropdown Option** behind it, and ADR-0011 as coded forbids it: `renderFieldMappings()` and `dropdownOptionsFor()` both map over the same `groupByField()` result with no filter and no discriminator between them, and `spec/unit/build-catalogue.test.ts` asserts the two sinks agree value for value in both directions.

The important thing is that ADR-0011's _argument_ never forbade it. Its stated failure mode runs one way only: "A Dropdown Option with no matching Mapping value is an Unmatched Value: the user selects their machine, no Profile Link appears, and nothing is logged unless Debug Mode is on." That is an Option without a Mapping. A Mapping without an Option has no corresponding failure, because nobody can select a value that is not offered — the runtime already tolerates it completely, since `resolveProfileLinks` looks up the stored string in `urlsByValue` and never sees an options list at all. So the invariant is not equality between the sinks. It is that **every Dropdown Option has a Mapping behind it** — `Options ⊆ Mapping values` — and equality was simply the cheapest way to get there when every catalogue entry was a product.

Collection Links therefore live in their own array, returned as a third output of `buildCatalogue` and committed as its own file. `renderFieldMappings` takes both arrays and concatenates; `dropdownOptionsFor` takes only the Resolved Products. The asymmetry is then structural: `dropdownOptionsFor` cannot emit a Collection Link because it is never given one.

That is the whole reason for the second array, and it is ADR-0011's own reasoning applied to a new case. The obvious alternative was a `kind: "product" | "collection"` discriminator on `ResolvedProduct`, with `dropdownOptionsFor` filtering on it. It was rejected because it converts a guarantee back into a habit — every present and future consumer of the catalogue has to remember the filter, and the first one that forgets offers a discontinued machine to a new member, which is the specific bug ADR-0012 was right about. ADR-0011 chose one file over two lists on exactly this basis: "Deriving the two lists independently would make that a matter of discipline; deriving them from one file makes it impossible to _generate_ them inconsistently." Two arrays and one concatenation keeps that property. A `kind` flag does not.

Sentinel values were rejected for a smaller reason and a larger one. The smaller: a `ResolvedProduct` requires a non-empty `handle` and a member of `ProductStatus`, and `readResolvedProducts` hard-fails on both, so a collection entry would need the reader relaxed for every row to admit one. The larger: `CONTEXT.md` defines a **Resolved Product** as a Suggested Title joined to a live product, and `data/resolved-products.csv` is the file two sinks and a digest are built from. Making it mean two things quietly is how the next person misreads all of it.

The cross-sink test changes from an equality assertion to a subset one, and it must assert the asymmetry _deliberately_ — with a fixture containing a Collection Link and a comment saying why it is expected to be absent from the options. The current test would fail the moment a Collection Link exists, which is correct today and would look like a regression tomorrow; the risk is that someone restores equality to make it pass and silently re-couples the sinks.

## Apply, and what it must not report as drift

A Catalogue Apply now writes fewer Dropdown Options than there are Mappings, on purpose. Two places notice. `componentDrift()` compares an instance's live Mappings against the catalogue and must learn that the difference is intended. More importantly, the four legacy catch-all values already exist as hand-entered options on instances that received the April 2026 run, and `dropdownOptionsFor` no longer emits them, so `planApply` will propose removing them. That removal is correct — offering a new member a discontinued machine is the thing we are trying not to do — but wherever it takes away a value the catalogue still carries as a Collection Link, it must be reported as its own disposition, saying that the value was removed as an option and retained as a link, in one breath. ADR-0013 makes a destructive write authorised by what it removes, and a plan that reads as a bare removal invites the next person to re-add them. (Whether the four catch-alls _specifically_ end up in that disposition depends on the curated assignment, which is not this section's concern — see "A retained removal cannot target anything this pipeline writes" below for where that landed.)

**One assumption here is load-bearing and unverified.** All of this depends on Discourse preserving a member's stored field value after the corresponding Dropdown Option is removed. ADR-0011 implies it does — it warns that "a user holding a removed value silently stops getting a Profile Link", which presumes the value is still there — but ADR-0015 found that the two operations which reduce a dropdown to zero options "destroy every value Users have stored". Removing some options is not the same operation as emptying the field, and the difference is the entire feature. This must be proved against the staging instance before any apply runs in production; if stored values do not survive, Collection Links for `Machine` and `Mask` need a different delivery than option removal, and only `Humidifier` — a text field, with no options at all — works as designed.

There is also a second author of the option list. Discourse's importer has until now extended custom-field option lists on every run, which would re-add the values this decision removes. Gerhard Schlager has offered to change that. Until he confirms it, an apply's filtered option list is not stable across import runs.

## The load-bearing assumption, verified (#41)

The paragraph above called the survival of a stored value across an option removal "load-bearing and unverified." #29 proved it first: it assigned a member's `Machine` value to `AirSense 11 AutoSet`, a known Dropdown Option, removed that option from the field definition, and read the member back. #41 proved the actual apply path on top of that — `planApply`'s removal-with-retention behaviour, not just Discourse's own persistence. `Machine` and `Mask` on `tyler-test.discourse.group` were each seeded with a per-equipment Collection Link value (`AirCurve 11 ASV (Discontinued)`, `3B Medical Siesta Full Face CPAP Mask (Discontinued)`) — not the four generic catch-alls ADR-0020 retired, which carry no shipped Collection Link and are a different case (below). `planApply` reported both seeded values as covered removals with a `RetainedLink`, `--replace` removed them, and the instance's own readback — a fresh `GET`, not the `200` from the write — confirmed neither option remained. So the two-branch design #41's issue body once described (remove vs. treat as absent-by-design) is closed for good: removal is safe regardless of what Discourse's importer does in between, exactly as the ticket's discussion concluded before any code ran.

**This does not retire the previous paragraph's second half.** Whether the importer keeps re-adding these values on every run is still real and still open — it decides how often a Catalogue Apply has to clean the list back up, not whether it may.

## A retained removal cannot target anything this pipeline writes

This is narrower than every removal `planApply` proposes. An ordinary `replace` can remove an option this pipeline wrote in an earlier run and has since dropped from the catalogue — a product that stopped resolving is exactly what a routine `replace` is for, and nothing stops that option from being one of this pipeline's own. What cannot happen is a _retained_ removal — one `planApply` reports as a `RetainedLink` — targeting such an option, because `dropdownOptionsFor` reads only Resolved Products, a Collection Link never reaches it (this ADR's whole point), and `readCollectionLinks` requires every value to carry the literal suffix `COLLECTION_LINK_SUFFIX` (` (Discontinued)`) that nothing on the catalogue path ever appends to a Resolved Product's value. So a Dropdown Option this pipeline derives and a Collection Link value can never be the same string — not "does not happen to collide today," but structurally cannot, for as long as this ADR holds.

On real data this cuts the other way for the four generic catch-alls (`CPAP Machines (Discontinued)` and its three siblings) that Discourse's importer hand-entered on the instances that received the April 2026 run: ADR-0020 retired those four as _values_ — a row that carried one now takes its own equipment name instead — so as of this writing none of the four appears anywhere in the shipped `data/collection-links.csv`. Removing one today is therefore an ordinary, unretained removal on real data, the same as any other option a person typed in that the catalogue no longer carries; `spec/unit/plan-apply.test.ts`'s `CATCH_ALLS` fixture exercises the _retained_ case instead, pairing the four titles with links it constructs for the test rather than the shipped ones, and its own comment says as much ("the shipped file carries `DreamStation CPAP Machine (Discontinued)` and never `CPAP Machines (Discontinued)`"). The per-equipment values #41 seeded are the kind that do have a shipped Collection Link behind them, which is why they were the ones chosen to exercise retention against a live instance. A reader comparing the committed catalogue and links files head-on could reasonably conclude the retention path is dead code, because nothing this repository produces ever needs it. It is not dead: it exists to retain whatever value a shipped Collection Link happens to name, which today is the per-equipment titles and not the four catch-alls — and that assignment is a curation choice (see below), not a structural one, so it can change.

## Where the curated assignment lives

The collection assigned to each value is a reviewed table, maintained as a tab in a cpap.com-specific Google Sheet and pulled into the repo as a **Sheet Export** by `scripts/export-sheet.ts`, exactly like the three option tables. It is not a TypeScript constant, because the people who make the judgement are not the people who deploy, and it is not a one-time paste, because ADR-0020 makes this a standing mechanism. Every curation change then lands as a reviewable Catalogue Refresh diff, which is what a Catalogue Refresh is for.

The tab carries a `Disposition` of `collection`, `plain-text`, `resolves-to-product` or `undecided`, and an `Override` column for correcting a recommended collection. `resolves-to-product` is the row that turned out not to need a Collection Link at all — the Suggested Title still names something cpap.com sells, so the ordinary catalogue path resolves it and this table stands aside. It is a curator's recorded decision like the first two, and only the absence of one blocks anything. `undecided` **blocks the ship** rather than emitting nothing. This mirrors an **Unresolved URL**: no evidence either way is not a pass and not a failure, so it stops the release and is resolved rather than absorbed. The alternative — treating an uncurated row as "no link" — was rejected because it is indistinguishable from the pre-ADR-0020 behaviour, so a newly discontinued product would silently degrade to no Profile Link and the mechanism would stop working with nothing to show it had.
