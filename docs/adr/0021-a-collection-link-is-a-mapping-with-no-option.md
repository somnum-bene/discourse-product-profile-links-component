# A Collection Link is a Mapping with no Dropdown Option

> **Refines [ADR-0011](0011-dropdown-options-are-a-second-sink-applied-per-site.md)** rather than superseding it. The invariant it protects survives; the equality it was implemented as does not. Required by [ADR-0020](0020-discontinued-equipment-links-to-a-collection.md).

A **Collection Link** must resolve for a member who already holds the value and must never be offered to a member choosing one. That is a **Mapping** with no **Dropdown Option** behind it, and ADR-0011 as coded forbids it: `renderFieldMappings()` and `dropdownOptionsFor()` both map over the same `groupByField()` result with no filter and no discriminator between them, and `spec/unit/build-catalogue.test.ts` asserts the two sinks agree value for value in both directions.

The important thing is that ADR-0011's *argument* never forbade it. Its stated failure mode runs one way only: "A Dropdown Option with no matching Mapping value is an Unmatched Value: the user selects their machine, no Profile Link appears, and nothing is logged unless Debug Mode is on." That is an Option without a Mapping. A Mapping without an Option has no corresponding failure, because nobody can select a value that is not offered — the runtime already tolerates it completely, since `resolveProfileLinks` looks up the stored string in `urlsByValue` and never sees an options list at all. So the invariant is not equality between the sinks. It is that **every Dropdown Option has a Mapping behind it** — `Options ⊆ Mapping values` — and equality was simply the cheapest way to get there when every catalogue entry was a product.

Collection Links therefore live in their own array, returned as a third output of `buildCatalogue` and committed as its own file. `renderFieldMappings` takes both arrays and concatenates; `dropdownOptionsFor` takes only the Resolved Products. The asymmetry is then structural: `dropdownOptionsFor` cannot emit a Collection Link because it is never given one.

That is the whole reason for the second array, and it is ADR-0011's own reasoning applied to a new case. The obvious alternative was a `kind: "product" | "collection"` discriminator on `ResolvedProduct`, with `dropdownOptionsFor` filtering on it. It was rejected because it converts a guarantee back into a habit — every present and future consumer of the catalogue has to remember the filter, and the first one that forgets offers a discontinued machine to a new member, which is the specific bug ADR-0012 was right about. ADR-0011 chose one file over two lists on exactly this basis: "Deriving the two lists independently would make that a matter of discipline; deriving them from one file makes it impossible to *generate* them inconsistently." Two arrays and one concatenation keeps that property. A `kind` flag does not.

Sentinel values were rejected for a smaller reason and a larger one. The smaller: a `ResolvedProduct` requires a non-empty `handle` and a member of `ProductStatus`, and `readResolvedProducts` hard-fails on both, so a collection entry would need the reader relaxed for every row to admit one. The larger: `CONTEXT.md` defines a **Resolved Product** as a Suggested Title joined to a live product, and `data/resolved-products.csv` is the file two sinks and a digest are built from. Making it mean two things quietly is how the next person misreads all of it.

The cross-sink test changes from an equality assertion to a subset one, and it must assert the asymmetry *deliberately* — with a fixture containing a Collection Link and a comment saying why it is expected to be absent from the options. The current test would fail the moment a Collection Link exists, which is correct today and would look like a regression tomorrow; the risk is that someone restores equality to make it pass and silently re-couples the sinks.

## Apply, and what it must not report as drift

A Catalogue Apply now writes fewer Dropdown Options than there are Mappings, on purpose. Two places notice. `componentDrift()` compares an instance's live Mappings against the catalogue and must learn that the difference is intended. More importantly, the four legacy catch-all values already exist as hand-entered options on instances that received the April 2026 run, and `dropdownOptionsFor` no longer emits them, so `planApply` will propose removing them. That removal is correct — offering a new member a discontinued machine is the thing we are trying not to do — but it must be reported as its own disposition, saying that the value was removed as an option and retained as a link, in one breath. ADR-0013 makes a destructive write authorised by what it removes, and a plan that reads as a bare removal invites the next person to re-add them.

**One assumption here is load-bearing and unverified.** All of this depends on Discourse preserving a member's stored field value after the corresponding Dropdown Option is removed. ADR-0011 implies it does — it warns that "a user holding a removed value silently stops getting a Profile Link", which presumes the value is still there — but ADR-0015 found that the two operations which reduce a dropdown to zero options "destroy every value Users have stored". Removing some options is not the same operation as emptying the field, and the difference is the entire feature. This must be proved against the staging instance before any apply runs in production; if stored values do not survive, Collection Links for `Machine` and `Mask` need a different delivery than option removal, and only `Humidifier` — a text field, with no options at all — works as designed.

There is also a second author of the option list. Discourse's importer has until now extended custom-field option lists on every run, which would re-add the values this decision removes. Gerhard Schlager has offered to change that. Until he confirms it, an apply's filtered option list is not stable across import runs.

## Where the curated assignment lives

The collection assigned to each value is a reviewed table, maintained as a tab in a cpap.com-specific Google Sheet and pulled into the repo as a **Sheet Export** by `scripts/export-sheet.ts`, exactly like the three option tables. It is not a TypeScript constant, because the people who make the judgement are not the people who deploy, and it is not a one-time paste, because ADR-0020 makes this a standing mechanism. Every curation change then lands as a reviewable Catalogue Refresh diff, which is what a Catalogue Refresh is for.

The tab carries a `Disposition` of `collection`, `plain-text`, or `undecided`, and an `Override` column for correcting a recommended collection. `undecided` **blocks the ship** rather than emitting nothing. This mirrors an **Unresolved URL**: no evidence either way is not a pass and not a failure, so it stops the release and is resolved rather than absorbed. The alternative — treating an uncurated row as "no link" — was rejected because it is indistinguishable from the pre-ADR-0020 behaviour, so a newly discontinued product would silently degrade to no Profile Link and the mechanism would stop working with nothing to show it had.
