# Dropdown Options are a second sink, applied per site by script

The catalogue feeds two places that must agree exactly, and only one of them is in this repository. Mappings live in `profile_link_fields` and ship as a committed default (ADR-0008). Dropdown Options live in Discourse site data at `/admin/customize/user_fields`, which no commit can reach. A per-site step therefore exists no matter how the Mappings are delivered.

That step is a script against the Discourse admin API, reading `DISCOURSE_BASE_URL`, `DISCOURSE_API_USERNAME` and `DISCOURSE_API_KEY` from an ignored `.env`. The base URL is the entire difference between test and production, so the same commit targets either subdomain by changing one variable — which is what "repeatable on a different subdomain" turned out to mean in practice. On Discourse 2026.8 the field definitions are read from `/admin/config/user_fields.json`; the older `/admin/customize/user_fields.json` path returns 404 and will mislead anyone who trusts the admin UI's own URL.

Both sinks are generated from the same `data/resolved-products.csv`, because drift between them is the failure this component is worst at surfacing. A Dropdown Option with no matching Mapping value is an Unmatched Value: the user selects their machine, no Profile Link appears, and nothing is logged unless Debug Mode is on. Deriving the two lists independently would make that a matter of discipline; deriving them from one file makes it impossible to *generate* them inconsistently.

That is a narrower guarantee than it first appears, and the difference matters. The two sinks land at different times by different mechanisms — one in a deployment, one in a command run by hand — so a stale deployment, a partially completed write, or an edit through the admin UI can still pull them apart on a live instance, with every test passing. So the script re-reads the field definitions after writing and compares the live option lists against the Mapping values in the checked-out catalogue, and it is safe to run twice, so an interrupted run is repeated rather than repaired. The catalogue also carries a digest that `settings.yml` records, so applying a catalogue newer than the component deployed to that instance is a warning rather than a silent success.

The script must be able to replace an option list, not only extend one. The `Machine`, `Mask` and `Humidifier` fields already existed with hand-entered options on the test instance, including a `DreamStation` / `Dreamstation` case-duplicate, so "add only" was never sufficient. The strongest case for replacement surfaced during the ADR-0008 spike: the instance's Machine options carry trademark symbols — `AirCurve™ 11 VAuto with HumidAir™` — and the corresponding Suggested Titles do not. Under exact-match those two strings are unrelated, so an "add only" run would leave the hand-entered options in place and every user holding one would silently stop resolving. A mismatch that fine is not going to be caught by reading the two lists side by side. Replacement is destructive to site data in a way that is invisible afterwards — a user holding a removed value silently stops getting a Profile Link — so the script refuses to run when it finds pre-existing options it did not write, until `--replace` is passed explicitly, and prints a before-and-after list either way.

## Consequences

A Custom User Field with no Mappings behind it is worse than an empty one, because it offers the user a choice that leads nowhere. `Humidifier` is in that state on the test instance and its Mappings are deferred (ADR-0012), so the apply step clears its options and leaves the field in place, unmapped, rather than leaving four selectable values that resolve to nothing.
