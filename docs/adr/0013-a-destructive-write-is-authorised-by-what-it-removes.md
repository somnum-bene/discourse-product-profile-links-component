# A destructive write is authorised by what it removes, not by who wrote an option

The Catalogue Apply has to decide whether it may overwrite a Custom User Field's Dropdown Options, and ADR-0011 already settled that it refuses when it finds pre-existing options it did not write. Implementing that sentence exposed the problem in it: there is nowhere to record that this pipeline wrote an option. Discourse stores a field's options as a list of strings and nothing else, so an option we wrote from last month's catalogue and an option an administrator typed into the admin UI are the same bytes. Authorship is not recoverable, and any scheme for recovering it — a marker character, a naming convention, a sidecar record in a theme setting — would put a fingerprint into text a User sees in a dropdown, to answer a question the next paragraph answers without one.

So the plan reasons about removal instead. An option the catalogue still carries is kept, because keeping it costs nothing and asks nobody to approve anything. An option the catalogue does not carry is one the write would take away, and that is the only case worth a human decision, because it is the one that changes what a User already holds: a User whose stored value disappears from the option list silently stops getting a Profile Link, and nothing is logged unless Debug Mode is on. `replace` authorises removal, and the refusal that demands it names every option it would remove.

This treats an option we wrote from an older catalogue as if a person had entered it, which means a routine catalogue change asks for `replace` again rather than proceeding on the strength of having run before. That is the conservative direction of the same uncertainty, and it is the one worth taking: the cost is a flag on a command an operator is already watching, and the cost of the other direction is silently deleting something a person typed.

Exact matching is what makes the question sharp, and it is not negotiable — Discourse stores what the User picked, and a Mapping either equals it or resolves nothing. But it also makes a real case hostile to read. The test instance's `Machine` options are the catalogue's own products spelled with trademark symbols, `AirCurve™ 11 VAuto with HumidAir™` against `AirCurve 11 VAuto with HumidAir`, so the plan correctly reports two removals and two additions that a person scanning the two lists would swear were the same four entries. The refusal therefore annotates each removed option with the target option it is probably a respelling of, comparing the two with every non-alphanumeric character dropped. That comparison decides nothing. It exists so the operator approving the replace knows whether they are deleting four unrelated products or four differently-typed spellings, and it stays out of the matching path entirely — the moment it influenced a write, "close enough" would be shipping to a dropdown.

## Consequences

The plan is all-or-nothing: a refusal on one field empties the write list for every field. On the test instance today that is not hypothetical — `Machine` refuses over its trademark spellings while `Mask`'s single hand-entered option happens to match a Mapping exactly and would have been safe on its own. Applying half of a plan produces a site that is neither configured nor unconfigured, and the operator's next move is the same either way: read what the plan says it would remove, then decide.

Clearing a field is authorised by naming it, not by `replace`. `Humidifier` is the only field in that state (ADR-0012), and it is emptied only when it is named, so emptying it can never ride along on populating `Machine` and `Mask`. Naming a field that does not exist on the instance is refused rather than ignored, because a request to destroy site data that quietly does nothing means the name is wrong or the instance is.
